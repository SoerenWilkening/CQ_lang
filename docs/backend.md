# CQ_lang Backend Architecture

The Stage 4 → binary half of the CQ compilation pipeline. Companion to
[`architecture.md`](./architecture.md), which covers Stages 1–4
(`.c` source through clean LLVM IR). This document starts where that
one leaves off.

Captures the design discussions of 2026-05-21 and 2026-05-22, with the
handle-based runtime ABI, mid → handle rebinding, and per-width mid
types as the load-bearing decisions.

Companion documents:
- [`architecture.md`](./architecture.md) — front-end pipeline, AST
  rewriter, intrinsic surface, three-level qint_t model
- [`example.md`](./example.md) — worked end-to-end example through
  Stage 4
- [`bennett-jl-comparison.md`](./bennett-jl-comparison.md) — design
  convergences with Sturm.jl / Bennett.jl / Orkan
- [`pipeline-sketch.md`](./pipeline-sketch.md) — original whiteboard
  sketch

## 1. Scope

This document defines:

- The Stage 4 LLVM IR **input contract** the backend expects
- The **mid → backend rebinding**: how `q*_mid_t` SSA values become
  opaque qubit handles inside the IR pass
- The **IR pass** algorithms: taint propagation, specialization,
  classification, uncomputation, template selection, lowering, inverse
  generation, region handling, manual inversion
- The **runtime ABI**: the handle-based contract between IR-emitted
  code and `libcq_runtime`, with the rich `qreg_state_t` living inside
  the runtime
- The **template library**: how the 38-opcode reversible primitives
  are distributed, indexed, and selected
- The **linkage discipline**: what tools must do at link time for the
  compiled binary to be complete

It does **not** define:

- Stages 1–4 (AST rewriter, intrinsic surface design, three-level
  model) — see [`architecture.md`](./architecture.md)
- Specific opcode-template circuit families (ripple-carry vs. Cuccaro
  vs. Draper, ancilla strategies) — deferred to backend-design time
- Simulator internals (statevector representation, density matrix
  support, noise models)
- Hardware backend transport (calibration, gate compilation to native
  ISAs, connectivity-aware routing)

## 2. Architectural principles

These extend the P1–P9 principles in
[`architecture.md`](./architecture.md) §2. They are specific to the
backend.

### B1. Handle-based runtime ABI

IR-emitted code references qubit registers only through opaque integer
handles. The runtime owns all rich state (qubit indices, classical
shadow, superposition mask, allocation tracking). No rich struct ever
appears in a function signature reachable from compiled IR.

Same pattern as POSIX file descriptors + the kernel's file table,
OpenGL handles + the GPU driver's resource state, JNI references +
the JVM's object table, CUDA streams + the driver's state. The
architecture has no quantum-specific quirk here — it's exactly the
standard pattern for managing rich runtime state from a compiled
program.

### B2. The mid layer dissolves at the IR pass

`q*_mid_t` is a front-end fiction. It exists only to carry quantum-ness
through Clang's mem2reg/sroa optimization without losing the signal.
The IR pass replaces every `q*_mid_t` SSA value with an `i32` handle,
rewrites function signatures, and the struct type stops appearing in
the IR. After the pass: no `q*_mid_t`, no tainted stock opcodes, no
`@cq_*` intrinsics — only `cqrt_*` runtime calls and classical control
flow.

### B3. Stock LLVM optimizations are inherited

Standard LLVM passes (mem2reg, sroa, GVN, DCE, inlining, constant
folding, LICM, scalar evolution, etc.) operate over the IR before the
CQ pass runs. We get all of them for free for the classical side of
any mixed program, and many of them improve specialization candidates
(smaller IR after inlining → faster classification, simpler templates).

**Discipline**: `@cq_*` and `cqrt_*` intrinsics must be marked
side-effecting (`nounwind` is fine; `readnone` / `readonly` would be
wrong) so LLVM does not CSE/DCE them across quantum-semantic
boundaries. Two `@cq_init_i32(0)` calls produce *two distinct
registers* — they must not be folded. Routine intrinsic-attribute
discipline; Enzyme and ASan do the same thing.

### B4. The "38" is the template surface, not a hard count

LLVM IR has roughly 38 data-carrying opcodes (per Bennett's analysis)
that need reversible templates. Stage 4 surfaces them as canonical
SSA. The backend's template library covers this fixed alphabet,
parametrized by operand width. So the count of distributed templates
is roughly `38 × widths × variants` — not 38, but indexed by 38.

### B5. Per-op uncomputation, mechanical inverses

Preserves ROADMAP §2 and [`architecture.md`](./architecture.md) P5/P6.
Uncomputation is emitted at SSA live-range ends, per tainted value,
not per function call. Inverses are generated by walking forward
templates in reverse and adjointing each gate. The backend ships
**forward + controlled** templates only; adjoint and
controlled-adjoint are derived.

### B6. Multiple runtimes share one IR

The IR pass and template library are runtime-agnostic. Different
`libcq_runtime` variants produce different output (OpenQASM, in-memory
circuit object, live statevector simulation, hardware transport,
etc.). The same compiled binary's behavior is determined at link time
by which runtime it binds against.

This is the natural extension of B1. The handle is the abstraction
boundary; whatever the runtime does behind that boundary is its
concern, including short-circuiting circuit construction in favor of
direct simulation.

## 3. Input contract — Stage 4 LLVM IR

What the backend receives from the front-end (rewriter + Clang codegen
+ `-O1` mem2reg/sroa cleanup):

### 3.1 IR shape

- Stock LLVM IR — no custom opcodes, no MLIR dialect, no LLVM fork
- Standard SSA form, post-mem2reg / post-sroa
- `qbool_mid_t`, `qchar_mid_t`, `qshort_mid_t`, `qint_mid_t`,
  `qlong_mid_t`, `qfloat_mid_t`, `qdouble_mid_t` struct types preserved
  at function-signature boundaries (inside bodies, mem2reg/sroa has
  likely flattened them to scalar `i1`/`i8`/`i16`/`i32`/`i64`/`float`/
  `double` SSA values)
- `@cq_*` intrinsic declarations preserved as external calls — see
  [`architecture.md`](./architecture.md) §6 for the surface
- Source-location debug info via `!dbg` metadata, for backend
  diagnostics in user-source terms

### 3.2 The intrinsic surface (recap)

Per-width construction (taint sources):
```c
qbool_mid_t   cq_init_i1 (int8_t  value);
qchar_mid_t   cq_init_i8 (int8_t  value);
qshort_mid_t  cq_init_i16(int16_t value);
qint_mid_t    cq_init_i32(int32_t value);
qlong_mid_t   cq_init_i64(int64_t value);
qfloat_mid_t  cq_init_f32(float   value);
qdouble_mid_t cq_init_f64(double  value);
```

Measurement (taint sinks, per-type family):
```c
int8_t  cq_measure_i1 (qbool_mid_t);     /* {0,1} measurement */
int8_t  cq_measure_i8 (qchar_mid_t);
int16_t cq_measure_i16(qshort_mid_t);
int32_t cq_measure_i32(qint_mid_t);
int64_t cq_measure_i64(qlong_mid_t);
float   cq_measure_f32(qfloat_mid_t);
double  cq_measure_f64(qdouble_mid_t);
```

Quantum-specific primitives:
```c
void cq_theta(/* q*_mid_t* */ q, double angle);   // R_y rotation
void cq_phi  (/* q*_mid_t* */ q, double angle);   // R_z rotation
```

Region brackets:
```c
void cq_when_begin(/* q*_mid_t */ cond);
void cq_when_end  (void);
void cq_invert_begin(void);
void cq_invert_end  (void);
```

Specialization mangling (declaration-only):
```c
__cq_q_<f>_<arg-mask>(...)        // quantum specialization of f
__cq_invert_<f>(...)              // inverse specialization
```

### 3.3 Decisions made 2026-05-22

- **Per-width mid types** replace the single parameterized
  `qint_mid_t` of the initial architecture.md draft. Aligns IR's
  natural width (`add i8` vs `add i32`) with user intent.
  [`architecture.md`](./architecture.md) §3's *"or analogous for other
  widths"* is now concrete.
- **`num_bits` dropped from `cq_init`**. Per-width init intrinsics
  (`cq_init_i1`, `cq_init_i8`, `cq_init_i16`, `cq_init_i32`,
  `cq_init_i64`, `cq_init_f32`, `cq_init_f64`) take only the initial
  value. Width is implicit in the intrinsic name.
- **Floating-point widths first-class.** `qfloat_mid_t` /
  `qdouble_mid_t` join the integer family as first-class width
  members, not Phase 2 "stubs" as the ROADMAP previously hinted. The
  IR-pass surface is type-agnostic — same taint propagation (extended
  over `fadd`/`fsub`/`fmul`/`fdiv`/`frem`/`fcmp`/`fneg`/`sitofp`/
  `uitofp`/`fptosi`/`fptoui`/`fptrunc`/`fpext`), same specialization,
  same region handling, same uncomputation. Only the per-opcode
  templates differ: fp templates internally Bennett-wrap (forward →
  rounding-ancilla + CNOT-copy → reverse) to make rounding-induced
  information loss locally reversible. Template-internal: doesn't
  change the IR-pass interface (§5.8 `emit_inverse` still operates on
  the wrapped template's visible boundary; per-op uncomputation
  remains per-op). Half precision (`_Float16`, C23): front-end keyword
  + intrinsic-decl surface optional, template implementation deferred.
  `long double` deferred (platform-dependent width). `_Complex` falls
  out automatically — Clang lowers `_Complex float`/`_Complex double`
  to `{float, float}` / `{double, double}` structs at the LLVM IR
  level with pair-of-scalar fp arithmetic, so it requires no new
  intrinsic surface.
- **Per-type measurement intrinsics.** `cq_measure → i64` replaced by
  the per-type family in §3.2. Resolves §10 q6. Forced by fp (fp
  values can't be carried through an `i64` return); applied uniformly
  to int widths for symmetry.
- **Bitfield / sub-natural-width allocations** deferred — not needed
  through Phase 9. If reintroduced (e.g., for resource-constrained
  hardware), a separate `cq_init_iN_bits(value, n)` per-width variant
  can be added later without disturbing the main flow.

## 4. Mid → handle rebinding

The architectural seam where the front-end's signal-bearing structs
become backend qubit handles. §5.2 walks the algorithm; this section
establishes the contract.

### 4.1 Layer recap

| Layer | Representation | Owned by | Created at | Purpose |
|---|---|---|---|---|
| **Source** | `quantum int x;` (keyword + C type) | User | Source authoring | Surface intent |
| **Mid** | `qint_mid_t = struct { i32 val; }`, `qfloat_mid_t = struct { float val; }`, etc. (per IR width — int and fp) | Rewriter | Stage 2 (rewriter) | Signal-bearing struct that survives mem2reg/sroa at fn boundaries |
| **Backend** | `i32` handle, indexing `g_circuit.registers` | IR pass + runtime | Stage 5 (IR pass emits `cqrt_alloc_*`) | Opaque reference to a runtime-owned rich qubit-register record |

The mid struct dissolves entirely during the IR pass. After lowering
the IR contains no `q*_mid_t` types — only `i32` handles flowing
through `cqrt_*` calls.

### 4.2 Concrete rebinding example

```llvm
; PRE — Stage 4 IR (what the rewriter + Clang produced)
%a_struct = call %qint_mid_t @cq_init_i32(i32 3)
%a        = extractvalue %qint_mid_t %a_struct, 0     ; tainted i32 = 3
%b_struct = call %qint_mid_t @cq_init_i32(i32 5)
%b        = extractvalue %qint_mid_t %b_struct, 0     ; tainted i32 = 5
%c        = add i32 %a, %b                            ; tainted add
%c_struct = insertvalue %qint_mid_t poison, i32 %c, 0
%m        = call i64 @cq_measure(%qint_mid_t %c_struct)
```

```llvm
; POST — after IR pass (ready for stock LLVM codegen)
%h_a = call i32 @cqrt_alloc_classical_i32(i32 3)      ; "i32" = handle
%h_b = call i32 @cqrt_alloc_classical_i32(i32 5)
%h_c = call i32 @cqrt_alloc_i32()                     ; output register
call void @cq_template_add_i32(i32 %h_a, i32 %h_b, i32 %h_c)
%m   = call i64 @cqrt_measure(i32 %h_c)
```

The `i32` SSA type is identical pre- and post-pass; only the
**meaning** changes. Pre-pass: "tainted integer value." Post-pass:
"register handle, index into `g_circuit.registers`."

### 4.3 Function-signature rewriting

`q*_mid_t` parameters and returns are rewritten during specialization
(§5.3). A function with signature `qint_mid_t foo(qint_mid_t)` becomes,
after quantum specialization:

```
void __cq_q_foo_q1(i32 handle_in, i32 handle_out)
```

Output-by-handle convention (Bennett's wrap-the-whole-function form,
see [`architecture.md`](./architecture.md) §7.7): no struct return;
the caller provides the output handle, the callee writes into it.
Identical to OpenGL functions that take output buffer handles.

## 5. IR pass

The core of the backend. Runs after Clang's `-O1` cleanup. Input:
Stage 4 IR per §3. Output: IR with no `@cq_*` intrinsics, no tainted
stock opcodes, only `cqrt_*` runtime calls plus classical control
flow.

### 5.1 Forward taint propagation

Standard data-flow over SSA values, monotone, single pass over the SSA
DAG.

```
taint_sources = {
    return value of any @cq_init_* call,
    q*_mid_t-typed function parameters,
    extractvalue of any of the above,
}

taint(v) = true iff
    v ∈ taint_sources, OR
    any operand of v's producing instruction is tainted

taint_sinks = {
    @cq_measure call sites,    // i64 result is classical
}
```

After the pass:

- Every stock LLVM instruction whose result is tainted is a quantum
  operation.
- Every `@cq_*` intrinsic call is a quantum operation.
- Untainted instructions are classical, left alone.

Tainted `br i1` branch conditions indicate quantum control flow; the
rewriter is responsible for wrapping these in `cq_when_*` regions. The
IR pass sanity-checks and emits an error if it sees a tainted branch
without a containing when-region.

### 5.2 Mid → handle rebinding (algorithm)

After taint analysis, walk each function:

```
for each @cq_init_i<W>(value) call producing %v:
    emit:   %h = call i32 @cqrt_alloc_classical_i<W>(value)
    replace all uses of %v with %h
    erase the @cq_init_* call

for each extractvalue %q*_mid_t %s, 0 producing %v:
    %s was a struct holding the handle; %v takes the handle directly.
    replace uses of %v with the handle SSA value, erase the extractvalue.

for each insertvalue poison, i32 %v, 0:
    folded away; downstream consumers take %v (the handle) directly.

at function boundaries (signatures with q*_mid_t):
    rewrite to (i32, ..., i32) handles per §4.3's convention.
    update all call sites correspondingly.
```

After this transformation: no `q*_mid_t` struct types remain in the
IR. Subsequent passes (template substitution, lowering) operate on
handle SSA values only.

### 5.3 Call-graph specialization

Worklist algorithm. Same shape as
[`architecture.md`](./architecture.md) §7.2; reproduced here with the
handle convention applied:

```
worklist = { call sites where any arg is q*_mid_t-typed
             or (post-rebinding) is a tainted handle }
visited  = ∅

while worklist not empty:
    call = worklist.pop()
    spec_key = (target_fn, q-arg-mask)

    if spec_key ∈ visited: continue
    visited.add(spec_key)

    target_ir = resolve_ir(target_fn)
    if target_ir is None:
        emit diagnostic per §10 q1
        continue

    if not classify_reversibilizable(target_ir):
        emit diagnostic per §10 q1
        continue

    spec_body = synthesize_quantum_specialization(target_ir, q-arg-mask)
    cache[spec_key] = spec_body

    for each call within spec_body whose operands include tainted handles:
        worklist.push(call)
```

`synthesize_quantum_specialization` uses the same per-opcode template
substitution as the in-function lowering in §5.7 — taint propagation
on the target's IR (with q-args marked tainted from the start), then
template substitution on tainted instructions.

### 5.4 Reversibilizability classifier

Walk the candidate function's IR; reject on any of:

| Reject | Reason |
|---|---|
| inline asm | opaque |
| syscall | non-pure |
| `volatile` loads/stores | shared state |
| atomic instructions | shared state / non-determinism |
| EH (`invoke`, `landingpad`, `catchpad`) | non-reversible |
| `setjmp` / `longjmp` (libc decl) | non-local control |
| indirect calls to unresolved targets | unknown reversibilizability |
| unbounded recursion | possibly non-terminating |
| vector / SIMD intrinsics | not yet implemented |
| transcendental intrinsics without soft impl | future |

Accept on a clean pass. Diagnostics report the offending instruction
with source-location precision via `!dbg`.

### 5.5 Per-op uncomputation

Preserves ROADMAP §2; implementation moves from AST use-def to IR SSA
live-range analysis.

For each quantum-mode function being lowered:

1. Build an ordered list of tainted instructions (now: handle-producing
   instructions) in program order.
2. For each tainted handle, compute its last use via the SSA def-use
   graph.
3. At each last-use point (or at `@llvm.lifetime.end` for stack qint
   slots that survive flattening), emit the **adjoint** of the gate
   sequence that produced the handle. The adjoint is generated by
   `emit_inverse` (§5.8) from the forward template's lowered gate
   sequence.
4. After emission, `cqrt_free(handle)` returns the qubit indices to
   the runtime's pool.

**Exceptions** (no uncomputation emitted):
- The enclosing function is `main`. (No caller to clean up before.)
- The handle escapes via return-by-value (callee preserves it; caller
  uncomputes).
- The handle is explicitly handed off via a `cq_invert_*` region
  inversion.

### 5.6 Template selection

For each tainted stock opcode + width pair, multiple template
variants may exist:

- `add i32`: ripple-carry, Cuccaro, Draper QFT-based, carry-lookahead, …
- `mul i32`: schoolbook, Karatsuba, QFT-multiplier, …
- `icmp slt i32`: ripple-borrow, parallel-prefix, …

Selection mechanism (TBD per §10 q2):

- **Compiler flag** (`-fquantum-adder=cuccaro`)
- **Cost model** (minimize depth / minimize ancilla / minimize gate count)
- **Backend hint** (different `libcq_runtime` variants prefer different
  templates — e.g., a connectivity-constrained hardware backend may
  favor templates with fewer long-range gates)

The selected template is then emitted as a call: tainted
`add i32 %a, %b` → `call void @cq_template_add_i32_<variant>(i32 %h_a,
i32 %h_b, i32 %h_c)`. The template body is supplied by the precompiled
template library (§7) or inlined by the IR pass.

### 5.7 Lowering to runtime calls

After §5.2 (rebinding), §5.3 (specialization), §5.5 (uncomputation),
and §5.6 (selection), each tainted opcode and each `@cq_*` intrinsic
is replaced with one or more `cqrt_*` calls.

Lowering map (per-width variants implied):

| Tainted opcode / intrinsic | Lowered |
|---|---|
| `call @cq_init_i<W>(value)` | `cqrt_alloc_classical_i<W>(value)` → handle |
| `call @cq_init_f<W>(value)` | `cqrt_alloc_classical_f<W>(value)` → handle |
| tainted `add i<W> %a, %b` | template call (§5.6), expands to `cqrt_cnot` / `cqrt_toffoli` sequence on handle qubits |
| tainted `fadd f<W> %a, %b` | fp template call — internally Bennett-wrapped (forward + rounding-ancilla + reverse); see §7 |
| tainted `mul i<W> %a, %b` | template call, similar |
| tainted `fmul f<W> %a, %b` | fp template call, internally Bennett-wrapped |
| tainted `icmp <pred> i<W> %a, %b` | comparator template, produces a flag handle |
| tainted `fcmp <pred> f<W> %a, %b` | fp comparator template, produces a flag handle |
| tainted `sext` / `zext` / `trunc` | width-conversion template (often free for `zext` to wider widths) |
| tainted `fptrunc` / `fpext` | fp width-conversion template (rounding-ancilla on narrowing) |
| tainted `sitofp` / `uitofp` / `fptosi` / `fptoui` | int↔fp conversion template (rounding-ancilla on `fp→int`) |
| `call @cq_theta(q, θ)` | `cqrt_ry(handle(q), θ)` |
| `call @cq_phi(q, θ)` | `cqrt_rz(handle(q), θ)` |
| `call @cq_measure_i<W>(q) → i<W>` | `cqrt_measure_i<W>(handle(q)) → i<W>` |
| `call @cq_measure_f<W>(q) → f<W>` | `cqrt_measure_f<W>(handle(q)) → f<W>` |
| `cq_when_begin(q) … cq_when_end()` | each inner gate replaced by its controlled variant on `handle(q)` |
| `cq_invert_begin() … cq_invert_end()` | inner gate sequence reversed + adjointed per §5.8 |

After lowering: no `q*_mid_t`, no `@cq_*` calls, no tainted stock
opcodes. Only `cqrt_*` calls threaded by the original classical
control flow.

### 5.8 Inverse generation

```
emit_inverse(forward_sequence):
    for each gate g in reverse(forward_sequence):
        if g has a parameterized angle:  emit g with angle negated
        else:                            emit g as-is  (self-adjoint)
```

`cqrt_x` / `cqrt_cnot` / `cqrt_toffoli` are self-adjoint → emit
unchanged. `cqrt_ry(handle, θ)` inverse → `cqrt_ry(handle, -θ)`. Same
for `cqrt_rz`.

The backend thus ships **forward + controlled-forward** templates
only. Adjoint + controlled-adjoint are produced post-hoc by
`emit_inverse`. This is the §7 P6 promise from
[`architecture.md`](./architecture.md), made concrete.

### 5.9 Region handling

`cq_when_begin(q) … cq_when_end()` brackets a region whose gates
execute controlled on `q`. The IR pass:

1. Walks the IR linearly between the matched begin/end calls.
2. For each gate within the region (including those emitted by §5.7
   lowering of tainted opcodes), substitutes its controlled variant
   targeting `handle(q)` as the additional control.
3. Erases the bracket calls themselves.

Nested `cq_when_*` regions accumulate controls (Toffoli-style with
multiple conditions).

`cq_invert_begin() … cq_invert_end()` similarly brackets a region to
invert. The IR pass collects the gate sequence between begin/end,
applies `emit_inverse` per §5.8, and substitutes. Erases the
brackets.

### 5.10 Manual inversion via `invert(...)`

`invert(foo)(args)` in user source is lowered by the rewriter to
`__cq_invert_<foo>(args)` (mangled inverse-specialization call). The
IR pass synthesizes its body by:

1. Running `__cq_q_foo_<mask>(args)` synthesis (§5.3) if not already
   in cache.
2. Applying `emit_inverse` (§5.8) to the forward's gate sequence.
3. Caching the inverse specialization.

Distinct from auto-uncomputation (§5.5): auto-uncomputation runs
without user intervention at SSA live-range ends; manual inversion
applies the inverse of an explicit operation the user wants to undo
(e.g., de-preparing a state after a measurement, undoing oracle
preparation in phase estimation).

## 6. Runtime ABI

The contract between IR-emitted code and `libcq_runtime`. The handle
pattern is the load-bearing element; everything else is supporting
detail.

### 6.1 The handle pattern

IR-emitted code references qubit registers via opaque `i32` handles
(or `ptr` if a pointer-handle ABI is preferred — see §10 q5). The
runtime maintains an internal table of register state, indexed by
handle.

Why this pattern:

- ABI stability under struct evolution (runtime can add fields without
  recompiling the IR pass or the template library)
- Platform ABI quirks disappear (no struct-by-value lowering surprises
  — structs >16B get passed by hidden pointer on x86-64 SysV anyway,
  memcpy'd on Windows x64)
- Multiple runtime variants share one IR + one template library
- Reference identity is automatic (two calls referencing handle 7 mean
  the same register)

### 6.2 `qreg_state_t` — runtime-internal

The rich struct lives entirely inside `libcq_runtime`:

```c
// libcq_runtime — internal header (not part of public ABI)
typedef struct {
    int      *qubits;         // allocated qubit indices in the global pool
    unsigned  num_bits;       // width
    int64_t   value;          // classical shadow / measurement result
    uint64_t  mask;           // superposition bitmask (per-bit)
    bool      is_unsigned;    // signedness
    // future fields can be added without rebuilding compiled code
} qreg_state_t;
```

The fields mirror the project's existing `qint_t` definition (see
`qint.h` and `main.c`'s struct), now promoted to a runtime-internal
concern. Suggested rename: `qint_t` → `qreg_state_t` in the runtime's
internal header, leaving user-facing surface as just `quantum int`
and its width variants. The `qint_t` name from v1 has no role in the
new architecture.

### 6.3 The global circuit struct

Inside the runtime:

```c
// libcq_runtime — internal state
static struct {
    qreg_state_t *registers;        // indexed by handle
    size_t        num_registers;
    size_t        capacity;

    gate_t       *gate_sequence;    // the circuit being built
    size_t        num_gates;

    qubit_pool_t  qubit_pool;       // free/used qubit indices
    // ...runtime-specific bookkeeping
} g_circuit;
```

Lifetime: initialized at program start (or first `cqrt_*` call), torn
down at program exit (or on explicit `cqrt_finalize()`).

### 6.4 Handle-based API

The public ABI `libcq_runtime` exposes to IR-emitted code:

**Allocation** (per-width variants, int + fp):
```c
int cqrt_alloc_i1 (void);
int cqrt_alloc_i8 (void);
int cqrt_alloc_i16(void);
int cqrt_alloc_i32(void);
int cqrt_alloc_i64(void);
int cqrt_alloc_f32(void);
int cqrt_alloc_f64(void);
```

### 6.5 Hybrid quantum-classical tracking

The runtime's `qreg_state_t.value` and `.mask` carry the classical
shadow alongside the quantum register. Maintained by the runtime:

- At `cqrt_alloc_classical_i<W>(v)`: `.value = v`, `.mask = 0` (all
  bits classical).
- During gate emission for known-deterministic operations (Pauli-X,
  classical-shadow-preserving addition, etc.): `.value` updates
  analytically; `.mask` stays as-is.
- During gate emission for superposition-creating operations
  (Hadamard, Ry/Rz with non-special angles): `.mask` bits flip to
  indicate the affected bits are now in superposition.
- At `cqrt_measure(h)`: returns `.value` after collapse. The runtime
  decides whether to actually issue a measurement gate or
  short-circuit based on `.mask` — if `.mask == 0`, the value is
  already classical and no measurement is needed.

This is the ROADMAP's hybrid-data-representation principle, working
transparently. Phase 11 optimization passes can leverage `.value` /
`.mask` to elide gates when classical shadows make them no-ops.

### 6.6 Multiple runtime variants

Same compiled binary, different `libcq_runtime` implementations:

| Runtime | Behavior at each `cqrt_*` call |
|---|---|
| `libcq_runtime_qasm.so` | Append a line to an OpenQASM output stream |
| `libcq_runtime_circuit.so` | Append to an in-memory `Circuit` struct |
| `libcq_runtime_eager.so` | Apply the gate immediately to a statevector (Orkan's EagerContext style) |
| `libcq_runtime_density.so` | Apply to a density matrix; supports noise |
| `libcq_runtime_hw.so` | Serialize and dispatch to a hardware backend |

**Direct-execution short-circuit.** A runtime may bypass circuit
construction entirely and execute gates against simulator state
in-place. `libcq_runtime_eager.so` is exactly this — gates apply to
the statevector at the moment of call, no `gate_sequence` array
maintained, no `Circuit` object built. The handle ABI is identical;
only the runtime's internal behavior differs. Supported by design;
not a Phase 1–10 focus.

### 6.7 Versioning discipline

The handle ABI is the long-lived interchange point with simulators
and hardware. Versioning needs:

- Symbol versioning on `cqrt_*` functions (ELF symbol versions /
  Mach-O equivalents) so runtime upgrades don't silently break
  compiled binaries
- A `cqrt_abi_version()` query function for runtime–compiler–template
  three-way compatibility checks
- Documented deprecation policy for ABI evolution

Concrete versioning scheme: §10 q4.

## 7. Template library

The reversible-circuit primitives the IR pass substitutes in for
tainted LLVM opcodes.

### 7.1 Coverage

The 38 data-carrying LLVM IR opcodes (Bennett's analysis covers both
integer and floating-point), each at every applicable width:

```
int arith:   add, sub, mul, sdiv, udiv, srem, urem
int bitwise: and, or, xor, shl, lshr, ashr
int compare: icmp (eq, ne, slt, sgt, sle, sge, ult, ugt, ule, uge)
fp arith:    fadd, fsub, fmul, fdiv, frem, fneg
fp compare:  fcmp (oeq, one, olt, ogt, ole, oge, ueq, une, ult, ugt,
                   ule, uge, ord, uno)
cast:        sext, zext, trunc, bitcast, ptrtoint, inttoptr,
             fptrunc, fpext, sitofp, uitofp, fptosi, fptoui
memory:      load, store, gep         (Phase 8 — memory model)
control:     phi, select              (when in tainted regions)
intrinsic:   llvm.memcpy, llvm.memset, llvm.ctpop, ...   (subset)
```

Each at applicable widths: int opcodes at `i1, i8, i16, i32, i64`; fp
opcodes at `f32, f64`. Cross-domain casts (`sitofp` / `uitofp` /
`fptosi` / `fptoui`) span int×fp width pairs. Variants (ripple-carry
vs. Cuccaro adder, Bennett-internal rounding strategy for fp, etc.)
multiply the count by a small factor.

### 7.2 Distribution shapes

The same template can be distributed three ways, with tradeoffs:

| Shape | Where | Optimization | Note |
|---|---|---|---|
| **LLVM bitcode (`.bc`)** | `libcq_templates.bca` archive | LTO can inline + DCE the gate sequence | Cleanest; requires bitcode-aware link |
| **Native (`.a` / `.so`)** | `libcq_templates.{a,so}` | Call-boundary opaque to LLVM opt | Simplest distribution; one call per opcode |
| **Pass-internal IRBuilder** | Inside the IR pass binary | Full IR-builder access | No precompiled artifact; templates regenerated per build |

Recommended: ship `.bc` for default builds, fall back to `.a` for
deployment where LTO is impractical. Per-deployment choice, not
per-program.

### 7.3 Naming convention

```
cq_template_<opcode>_<width>[_<variant>]

Examples:
  cq_template_add_i32                       // default variant
  cq_template_add_i32_cuccaro               // explicit Cuccaro
  cq_template_mul_i16_karatsuba
  cq_template_icmp_slt_i64_parallelprefix
```

Each takes handle arguments (per §6.1) plus any necessary scalar
parameters (e.g., shift amount as a classical constant).

### 7.4 Variant selection

See §5.6. The selection policy is open (§10 q2). Default for Phase 2:
one canonical variant per opcode/width, chosen for ease of
implementation. Phase 11 introduces cost-model-driven selection.

## 8. Linkage and toolchain

### 8.1 Required toolchain

- **Clang** with libtooling (for the rewriter — front-end concern)
- **LLVM** with the CQ IR pass loadable as a pass plugin
  (`opt -load-pass-plugin libcq_pass.so -passes=cq-lowering`)
- **`libcq_templates.{bca,a,so}`** — the template library
- **`libcq_runtime_<variant>.so`** — one or more runtime variants
- **LTO-aware linker** (`ld.lld` recommended) for `.bc` template
  linking

### 8.2 Build flow

```
.c source
   │
   ▼ rewriter (front-end)
.transpiled.c
   │
   ▼ clang -emit-llvm -c
.bc                                  ← Stage 4 IR (this doc's input)
   │
   ▼ opt -load-pass-plugin libcq_pass.so -passes=cq-lowering
.lowered.bc                          ← post-IR-pass: only cqrt_* calls
   │
   ▼ clang (LTO link)
.o                                   ← stock x86/ARM machine code
   │
   ▼ ld (LTO; links templates + runtime)
binary                               ← executes → circuit built / streamed
```

### 8.3 Cross-language input (P9 from architecture.md)

Any function whose LLVM IR is reachable can participate in
quantum-specialization, regardless of source language. To bring in
C++, Rust, Fortran, etc.:

1. Compile with the language's `-emit-llvm` (or equivalent).
2. Include the resulting `.bc` in the LTO link.
3. The IR pass discovers callable functions via the call graph.
4. Specializations are synthesized on demand via §5.3.

Closed-source libraries without IR cannot be specialized. The IR pass
emits a diagnostic per §5.4 / §5.3.

### 8.4 Failure modes (per §10 q1)

- **Reachable function has no IR available**: default hard error;
  optional flag to insert measurement bridge.
- **Reachable function fails reversibilizability classifier**:
  default hard error; optional flag to insert measurement bridge per
  Sturm's choice.
- **Indirect call cannot be devirtualized**: hard error.

## 9. ROADMAP phase mapping

How each ROADMAP phase lands in the backend layer.
**[backend]** = owned by this doc; **[front-end]** = owned by
architecture.md; **[shared]** = spans both.

| Phase | Description | Layer |
|---|---|---|
| **1 — v1** | Basic qint, `+` only | [front-end] proof-of-pipeline at the rewriter layer |
| **2 — type system + `CQ.h`** | Per-width quantum types (int + fp first-class), theta/phi/invert markers | [shared] front-end emits intrinsics; backend declares the runtime template stubs (fp templates are stubbed until implementations land — front-end surface is complete) |
| **3 — full op set** | 38 opcodes × widths | [backend] template library expansion |
| **3.3 — classical-mask views** | `q & C` as zero-cost bit view | [backend] view materialization is an IR-pass operation |
| **3.4 — mixed-width promotion** | C-standard widening rules | [backend] templates for `sext`/`zext`/`trunc` per width pair |
| **4 — `if` (q-condition)** | Type-dispatched | [shared] rewriter emits brackets (§3.2); backend owns controlled-form substitution (§5.9) |
| **5 — auto uncomputation** | Per-op compile-time adjoints | [backend] §5.5 |
| **6 — for-loops** | Classical bounds | [backend] free: IR pass leaves loops intact; runtime accumulates per iteration |
| **7 — user-defined fns + inversion** | Function adjoint derivation | [backend] §5.3, §5.10 |
| **8 — memory: arrays/pointers** | Array indexing, pointer aliasing | [backend] LLVM alias analysis; Bennett-style memory strategies per allocation site |
| **9 — full C surface** | structs/unions/typedefs | [front-end] Clang lowers all of these correctly; rewriter handles AST shapes with quantum members |
| **10 — q-conditioned while** | Likely amplitude amplification | deferred |
| **11 — optimization passes** | Gate cancellation, ancilla reuse, fusion | [backend] standard LLVM-pass shapes operating on lowered IR (post §5.7) |

## 10. Open design questions

Backend-specific decisions still owed:

1. **Failure on non-reversibilizable callee.** Hard error / implicit
   measurement bridge / warn + bridge. Sturm chose warn + bridge;
   Phase 7 will pick.
2. **Variant selection policy.** Per-opcode flag / cost-model /
   backend-hint-driven. Phase 11 territory; Phase 2/3 ships one
   canonical variant per opcode.
3. **Specialization mangling scheme.** Concrete name format, ABI
   stability across compiler invocations for caching.
4. **Runtime ABI versioning.** Symbol-versioning scheme, ABI
   compatibility matrix (compiler ↔ templates ↔ runtime three-way).
5. **Handle representation: `i32` vs `ptr`.** `i32` is simpler,
   matches §6.4's sketch; `ptr` would let the runtime use real
   pointers behind the handle and gives LLVM's type system stronger
   guarantees (won't be confused with an ordinary integer).
6. **Per-type measurement intrinsics — RESOLVED 2026-05-22.** Per-type
   family adopted (`cqrt_measure_i<W> → i<W>`, `cqrt_measure_f<W> →
   f<W>`). Forced by fp support; applied uniformly to int widths for
   symmetry. See §3.2 / §6.4.
7. **Diagnostics location preservation.** `!dbg` survives most opt
   passes but not all. Minimum-acceptable fidelity for Phase 5+
   user-source error reporting.
8. **Bitfield / sub-natural-width allocation reintroduction.** When,
   how — a separate `cq_init_iN_bits(value, n)` family if and when
   needed.
9. **Multi-runtime ABI normalization.** When two runtimes diverge
   (e.g., one supports density matrices and one doesn't), how does
   the IR-emitted code know which is linked? Capability-query
   functions vs. link-time selection.

## 11. Glossary

(extends [`architecture.md`](./architecture.md) §13)

| Term | Meaning |
|---|---|
| Handle | Opaque `i32` (or `ptr`) reference to a qubit register, used by IR-emitted code. Indexes into `g_circuit.registers`. |
| `qreg_state_t` | Runtime-internal rich struct holding qubit indices, classical shadow, mask, etc. Replaces v1's `qint_t` as the runtime's internal name. |
| `g_circuit` | The runtime's global circuit-construction state: register table + gate sequence + qubit pool. |
| Template | Reversible-circuit implementation of one LLVM opcode at one width. Distributed in `libcq_templates`. |
| Template variant | An alternative implementation of the same opcode (ripple-carry vs. Cuccaro adder, schoolbook vs. Karatsuba multiplier, etc.). |
| Specialization | An IR-pass-synthesized function body where every tainted instruction is replaced by its template. Indexed by `(function, q-arg-mask)`. |
| Classical shadow | The `value` field in `qreg_state_t`, tracking the classical interpretation of a quantum register's state. ROADMAP hybrid-data-representation principle. |
| Direct-execution short-circuit | A `libcq_runtime` variant that applies gates to simulator state at call time instead of accumulating a circuit. `libcq_runtime_eager.so` style. |
| Mid → handle rebinding | The IR pass step that replaces `q*_mid_t` SSA values with `i32` handles, dissolves the mid struct type, and rewrites function signatures to the handle ABI. §4, §5.2. |
