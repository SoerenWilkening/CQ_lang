## Finding R2-1: the in-place-mark chronology comment is now false (documentation, newly stale)

`ir-pass/src/OpcodeLowering.cpp:1310-1313` argues that the eqpx recheck is inert in a clone because clones are built after `lowerLoops`. The new clone driver runs `runControlChain` (`Specialization.cpp:284`), which calls `lowerLoops(M, wd, taint)` (`StageList.cpp:101`) with the clone's own taint before `lowerOps`. Thus the stated chronological premise no longer holds.

The behavior is guarded correctly: the eqpx recheck is deliberately not gated by `inBennettClone` (`OpcodeLowering.cpp:1314-1332`), matching the unconditional Phase-2 dispatch on `InPlaceRailOps` (`:1427-1429`). No wrong lowering follows from the comment. Remove the chronological inertness claim rather than replacing it with an unproved claim that no clone can receive a mark. The coordinator has been notified; R9 calls for correcting this source comment in the same change.

## Non-finding R2-2: printed caller zeroext omission is not effective ABI loss in p4

The source p4 call passes `i1 zeroext %a` and `i1 zeroext %b` (`p4_ext_literal.ll:17`). Its fp-return retarget rebuilds the call through `retargetSite` (`Specialization.cpp:519-526`) and the lowered call prints no local zeroext (`p4_ext_literal.lowered.ll:18`). This rebuilding code is byte-identical on main. However, the new clone's unchanged i1 parameters still carry zeroext (`lowered.ll:24`).

LLVM 19 does not derive caller extension flags exclusively from the printed local attribute set. Its `TargetLoweringBase::ArgListEntry::setAttributes` asks `CallBase::paramHasAttr` for ZExt/SExt, and that method checks the local set and then the directly called function's parameter set. Thus the direct clone call retains effective zeroext, and the printed omission does not establish a miscompile or an exposed buggy population. Sources: [LLVM 19.1.7 TargetLowering.cpp, lines 102-108](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.7/llvm/lib/CodeGen/SelectionDAG/TargetLowering.cpp#L102), [LLVM 19.1.7 Instructions.cpp, lines 370-393](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.7/llvm/lib/IR/Instructions.cpp#L370).

I inspected code generation from the existing lowered p4 artifact without another cq-opt execution. `clang -S` on the shipped x86-64 target masks and zero-extends before the clone call and each i1 runtime call (`p4_ext_literal.x86.s`). `llc -O2` forwards the already-zeroext incoming arguments (`p4_ext_literal.llc-O2.s:54-64`); this is consistent with the source-level fallback above. No runtime result was measured. Other information `retargetSite` does not copy (e.g. calling convention or operand bundles) was not cleared by this narrow check.

This differs from the inverse-template declaration: its literal slots have no declaration zeroext, so the mechanical reverse must carry the forward's effective extension attribute onto the call. The new shared code does that at `EmitInverse.cpp:338-341`. In p4, both AND and OR forward calls have `i1 zeroext` at slot 1 and both `_unc` calls have it at slot 2 (`lowered.ll:28-29`, `:39-40`).

## Retype identity and side-ledger argument

`retypeCloneSignature` changes only masked reversible-fp slots and a predicted-tainted fp return (`SpecializeClone.cpp:304-319`). It inserts the replacement immediately before the old function, transfers name/attributes/metadata, and splices the body (`:324-331`). Every body instruction keeps identity; its new parent is the replacement. For every old argument, same-type uses are RAUW'd to the new argument (`:336-338`); changed-type uses are substituted explicitly (`:340-344`) until opcode lowering turns them into handle operations. All argument identities change when any signature slot changes, including masked integers and unmasked classical params.

The deletion callbacks drop old function/argument keys instead of allowing them to alias fresh allocations (`ScrubOnDelete.h:125-133`; `TaintPropagation.h:43-70`). These containers deliberately do not follow RAUW. The subsequent rebuilding therefore matters:

- `SpecPlan.Cache` retains its key `(original Callee, Mask)`; only its Clone value is replaced (`Specialization.cpp:554`, `:578-582`). No cache key points at the temporary clone. Recursion is declined before this build, and a site is retargeted only after finalization, so no recursive call or parent call requires RAUW of the erased function.
- The old `SpecHandleArgMask` function key self-scrubs; the new function receives the same mask (`:559`, `:582`). `SpecDeadArgMask` has not been written at replacement time: it is first recorded on the replacement later (`:751-753`). Twins are synthesized after their inner clone build completes and receive their shifted handle mask (`:706-710`).
- Every masked **new** argument is reinserted into cloneTaint, including same-type integer arguments (`:583-585`). Unmasked arguments remain classical. P1/P2/P4 and the classical index of P5 inspect that boundary dynamically; the masked-integer half is analytic only because P6 was invalid.
- HandleWidth is reconstructed on the new fp-handle argument from the original callee parameter type (`:594-598`), before casts are collected. P2 and P5 show the first cast recovers f32 and f64 respectively. Body-gate width and ownership keys survive the splice. BirthOrder keys for body gate producers keep identity; parameter birth order is not a seedClone record (`SpecializeSeed.cpp:18-49`).
- The control ledgers keyed on comparisons/gates/rails keep their body identities. Compare-read seed/operand entries use WeakTrackingVH (`TaintPropagation.h:943-949`); same-type argument RAUW follows, whereas a deleted changed-type argument can null an entry. Their clone-local re-asks already ran inside runControlChain (`StageList.cpp:256-277`) before retyping (`Specialization.cpp:284`, `:578`), so no later authorization depends on those erased-argument entries. Source rotations, measurement lists and I/O-function tape records are absent in an admitted classical callee; the body scan excludes that work. CloneTaint is disjoint from module taint and is not retained for a later main uncompute walk.

The local ClonePlan is consumed and destroyed in lowerCloneControl before the function is replaced. The persistent module Pending sites refer to original caller/callee functions, not this transient clone. The inspected calls and cache reuse in p1 support these identity arguments; neither verify-clean nor successful allocation is used as semantic evidence.

## Borrowed rails, whole-stream reversal and inBennettClone

The M-C in-place reassignment candidate is explicitly gated off in a Bennett clone (`OpcodeLowering.cpp:1339-1346`); the caller passes true (`Specialization.cpp:923`). Thus ordinary quantum arithmetic reads borrowed inputs and mints scratch. Loop-committed marks remain a separate route and receive the unconditional eqpx shape recheck; R2-1 corrects the stale claim about that route. Surviving rolled clones are still stopped by the single-block backstop; this round did not clear rolled clone reversal.

`lowerQramReads(..., true)` skips the top-level coherent-return fence, but retains the in-bounds check (`QramLowering.cpp:3411`, `:3431-3436`). P5's index is explicitly masked to four cells. Its value is copied to a fresh out before the QRAM `_unc`, and the index remains live until that `_unc` and is then reversed. The circuit therefore implements basis lookup coherently without freeing the output, collapsing the input, or leaving index garbage entangled with it. The nested twin recreates that same lookup, XORs the outer result to zero, and restores scratch by the same ordering.

The Bennett forward capture precedes its out allocation/copy; the fresh out is excluded from reversal (`BennettWrap.cpp:218-244`). The reverse walks all retained gates in reverse program order (`:249-255`), and final freeing only admits captured Mint results or zero-valued Alloc results (`:262-267`), never parameters. Strip-elision compositions beyond the p3/p4 networks are assigned to round 3 and are not cleared by this report.
