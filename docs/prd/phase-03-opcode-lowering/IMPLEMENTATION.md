# Phase 3 Implementation Plan — IR pass: full opcode lowering

Companion to [`PRD.md`](PRD.md). The PRD fixes *what* and *why*; this
document fixes *how, in what order, and how each step is proven*. It is
grounded in the current tree (`taint-driven-pipeline` branch), verified
file-by-file, not just the PRD prose.

**Guiding constraints (from the request):**

1. **Modular** — one responsibility per translation unit; no module
   folded into another. Phase 2's seam (taint / rotation / opcode /
   measure / width-dispatch / driver) is preserved; the single
   `OpcodeLowering` opcode arm is **split** into a driver + three
   instruction-class lowerers + two shared helpers, rather than grown
   past its budget.
2. **Test-driven** — every work package leads with the test that fails
   (RED), then the change that makes it pass (GREEN). Fixtures are
   first-class deliverables, authored before or with their code.
3. **≤ 300 LOC per hand-authored TU** — budgets tracked in §3.
   `runtime/cq_templates.{h,c}` is autogenerated from
   `tools/opcode_table.yaml` and is **out of budget**.

## 0. The headline: most of the *surface* already exists; the *pass* does not

Verified against the tree, two facts reshape this phase versus a naive
reading of the PRD:

- **The runtime ABI is already Phase-3-complete.** `opcode_table.yaml`
  already declares all 17 binary stems, `fneg`, both compare families
  (all 16 predicates), and all 68 cast pairs — each with `fwd`/`inv` and
  (for binary/compare) `_hl` variants. `runtime/cq_templates.{h,c}`
  already ship **680 generated symbols**. The tooling delta for Phase 3
  is tiny (§WP1): `one→une`, add `frem`, add `_lh` variants.
- **`gen_templates.py` needs a small, contained `_lh` extension.**
  Today `enumerate_all` emits a **hardcoded 4-variant grid** per binary
  op (`base`, `_hl`, `_inv`, `_hl_inv`), and `signature`/`stub_body`
  handle only arity-1, Q+Q, and `_hl` shapes — there is **no `_lh`**.
  Adding it means: make `enumerate_all` **variant-driven** (one row per
  token in each op's `variants` list, via a token→`(suffix, shape)` map
  that gains `fwd_lh→_lh`, `inv_lh→_lh_inv`), and add an `lh` branch to
  `signature`/`stub_body` (`int32_t sym(<ctype> a_classical, int32_t
  b_handle)`; printf order `(classical, h)`). `gen_templates_test.py`
  already keys per-kind counts on `len(op["variants"])`, so a
  variant-driven `enumerate_all` is the TDD-clean change (~+25 LOC). The
  680-symbol ABI is otherwise complete (all `_hl`/`_inv`, all compares,
  all casts, `fneg`).

So the load-bearing work is entirely **pass-side**: `OpcodeLowering`
today lowers only tainted `add`/`fadd` (Q+Q and Q+C); everything else —
the other 15 binary stems, `fneg`, `icmp`/`fcmp`, all casts, and the
`_lh` (literal-on-left) and predicate-flip canonicalizations — currently
hits the "no template" diagnostic. Phase 3 makes the pass emit the calls
the runtime is already waiting for.

One **discrepancy to reconcile** (see §11, Decision D1): the yaml header
(lines 3–7) and `gen_templates_test.py` still describe generating
`ir-pass/src/OpcodeTables.cpp` and `ir-pass/test/phase3/<op>/*.ll`, but
PRD §2.1 and §5 **supersede** that — the pass builds names
programmatically and does **not** generate/consume `OpcodeTables.cpp`,
and fixtures are hand-authored (skeletons may be generated, CHECK lines
real). Neither artifact is committed today, so this is a description /
test-assertion cleanup, not a file deletion.

## 1. The invariants that govern everything (state up front)

### 1.1 Handle typing (inherited from Phase 2 §1)

> A quantum register reference is always an `i32` handle; a classical
> value is always its real C width. They cross only at named boundaries.

Every tainted SSA value Phase 3 produces is an `i32` handle. The
classical operand of an `_hl`/`_lh` template is passed at its **real
LLVM width** (`i16`, `double`, …) to match the generated C signature
(`int16_t b_classical`, `double b_classical`). Real widths reappear only
there and at `cqrt_measure_<W>`.

### 1.2 The flag-handle invariant (new this phase)

A tainted `icmp`/`fcmp` lowers to a template that **returns `i32`** (a
flag handle, logically 1-qubit), never an `i1`. RAUW therefore replaces
an `i1` SSA value with an `i32` handle — a cross-type RAUW, **laundered
by erasure** exactly as in Phase 2 §1: every user of the compare result
is itself tainted, hence itself lowered to a call consuming an `i32`
handle and then erased. The transient mistyped instruction
(`zext i1 %flag_i32 …`) never reaches the verifier. The `flag handle
never reaches a terminator` — `br i32` exists at no point (§1.4 gate).

### 1.3 Cast width capture before RAUW (the single most error-prone point)

`CastInst::getSrcTy()` returns `getOperand(0)->getType()`. Once the
operand is RAUW'd to an `i32` handle, the **source width is lost**. The
driver therefore captures `(fromWidth, toWidth)` for every tainted cast
at **collection time**, before any lowering mutates an operand. This is
PRD §2.3 and risk R1; it is why collection is fully up-front.

The measured-compare bridge makes this concrete: Clang emits
`%c = icmp …` → `%z = zext i1 %c to i32` → `cqrt_measure_i32(%z)`.
Lowering the compare RAUWs `%c`(i1) to an `i32` flag handle; the `zext`
is now transiently `zext i1 <i32-value>`. Because its `(i1→i32)` widths
were captured *before* that RAUW, cast lowering emits
`cq_template_zext_i1_to_i32(flag)` and erases the malformed `zext`. The
bridge is correct **only** because of up-front capture.

### 1.4 Single program-order rewrite walk

Cross-class data flow runs both directions (a `sext` may feed an `add`;
an `add` may feed an `icmp`; an `icmp` may feed a `zext`→measure). To
keep producer-before-consumer without per-class ordering assumptions,
the driver does **one** function/BB-order collection over all four
classes, then rewrites in that order. When a consumer is reached its
operands are already template handles (RAUW propagated them) and already
in `taint.Tainted`. This generalizes the Phase-2 single-loop design that
already handles "binary consuming binary."

### 1.5 Standing guard

Every `*.ll` fixture keeps its second RUN line
(`… | %cq-opt -passes=verify -disable-output -`). For Phase 3 that line
is the guard for **both** the handle-typing and the flag-handle
cross-type RAUW (verified clean on this assertions-OFF LLVM-19
toolchain, Phase 2 §1; do not re-litigate).

## 3. Module decomposition & LOC budget (the ≤300 constraint)

The single `OpcodeLowering` opcode arm cannot hold four instruction
classes under 300. The split is by **semantic effect on the handle**:

```
                         ┌─────────────────────────────┐
                         │ OpcodeLowering (driver)      │  collect-in-order,
                         │  lowerOps(M, wd, taint)      │  classify, capture
                         └──────────────┬──────────────┘  cast widths, dispatch,
                                        │                  erase
        ┌───────────────────┬──────────┴──────────┬───────────────────┐
        ▼                   ▼                     ▼                   ▼
  ArithLowering       CompareLowering        CastLowering        (Phase-4 gate:
  binary+unary →      icmp/fcmp →            casts →              compare feeding
  data handle         flag handle            width-change         br/select left
        │                   │                     │                untouched)
        └─────────┬─────────┴──────────┬──────────┘
                  ▼                     ▼
           TemplateName          OpcodeSupport          WidthDispatch
           (pure name str)       (policy/classify,      (FunctionCallee:
                                  diagnostics)           name → Fn + type)
```

|---|---|---|---|
| `OpcodeLowering.cpp` | 219 | **~150** | becomes driver: ordered collect (~60), cast-width capture (~20), dispatch switch (~30), erase (~10), includes/comment (~30). |
| `OpcodeLowering.h` | 53 | ~40 | one `lowerOps` decl + contract comment. |
| `TemplateName.cpp` | — | **~70** | `dataName`, `compareName`, `castName`; pure. |

### WP3 — `ArithLowering` + driver refactor (binary all stems + `fneg`)

The first behavioral expansion. `OpcodeLowering` becomes the ordered
driver; binary/unary lowering moves out and widens to all stems.

- **RED.** Author per-(opcode,width,shape) fixtures (§6) for the new
  binary stems and `fneg`: a Q+C `mul` (`_hl`), a Q+Q `sub` (HH), an
  LH `sub` (literal on the left → `_lh`), a bitwise `shl`/`xor`, an
  `fneg`. Against the WP2 pass they hit "no template" → RED.
- **GREEN.**
  - **Driver (`OpcodeLowering::lowerOps`)** — single up-front walk over
    every function/BB in order; for each tainted instruction classify
    and enqueue:
    ```
    Work : vector<Instruction*>            // program order, gated
    CastW : DenseMap<CastInst*, CastWidths>
    for F, BB, I in module order, if taint.Tainted.count(&I):
        if BinaryOperator/UnaryOperator: Work.push(&I)
        elif CmpInst: if isDataPositionCompare(&I): Work.push(&I)  // else Phase 4
        elif CastInst: capture (abiWidthFromType(getSrcTy),
                                 abiWidthFromType(getDestTy)) → CastW; Work.push(&I)
    for I in Work:                          // rewrite in program order
        dispatch by dyn_cast → rewriteBinary / rewriteUnary
                              / rewriteCompare / rewriteCast(I, CastW[I])
    erase all of Work
    ```
    (Compare/cast dispatch arms are wired here but their lowerers land in
    WP4/WP5; until then no compare/cast is enqueued because no fixture
    introduces one — the build stays green.)
  - **`ArithLowering::rewriteBinary`** — generalizes the Phase-2 body:
    - `stem = binaryStem(opcode)`; empty → `diagnoseNoTemplate`.
    - `abi = abiWidthFromType(BO->getType())`; int/fp sanity as today.
    - Operand classification by `taint.Tainted` (authoritative — covers
      args/loads/literals), per PRD §2.4:
      - **HH** (both tainted): order by `BirthOrder` (lower→LHS); QQ
        template.
      - **HL** (one tainted): if `isCommutative`, canonicalize literal to
        RHS → `_hl(handle, classical)`. If non-commutative and the
        literal is on the **left** → `_lh(classical, handle)`; on the
        right → `_hl`. **The BirthOrder swap is gated to commutative ops
        only** (PRD §2.4).
    - Emit via `wd.dataTemplateFn(stem, abi, shape)`; carry `DebugLoc`;
      RAUW; `taint.Tainted.insert(T)`, `erase(BO-from-set)`,
      `BirthOrder[T] = NextBirth++`. (Identical bookkeeping to Phase 2.)
  - **`ArithLowering::rewriteUnary`** — `fneg` only; `(i32)→i32` unary
    template; RAUW; same bookkeeping.
- **Files:** `OpcodeLowering.{cpp,h}` (driver), `ArithLowering.{cpp,h}`,

### WP5 — `CastLowering` (early width capture, the zext/trunc bridge)

- **RED.** Fixtures: a representative widen (`sext i8→i32`), a narrow

## 5. Module algorithms (the tricky bits, precise)

### 5.1 Operand classification (`ArithLowering`, PRD §2.4)

`taint.Tainted` membership is authoritative for "is this operand a
handle" — **not** `isa<Constant>`, which would misclassify tainted-but-
constant-folded values and miss tainted args/loads (the existing
`lowering_q_plus_arg` fixture pins this).

| operands | op class | emit | order rule |
|---|---|---|---|
| H, H | any | QQ `cq_template_<stem>_<W>` | lower-`BirthOrder` → LHS |
| H, L / L, H | commutative | `_hl(handle, lit)` | literal → RHS; BirthOrder swap **on** |
| H, L | non-commutative | `_hl(handle, lit)` | literal already RHS |
| L, H | non-commutative | `_lh(lit, handle)` | literal on LHS; BirthOrder swap **off** |

LH arises from ordinary C surviving `-O1`: unary integer negate is
`sub …_lh` (literal 0); `100/x` → `sdiv …_lh`; `3<<x` → `shl …_lh`
(PRD §2.6).

### 5.2 Compare canonicalization (`CompareLowering`, PRD §2.4, §2.8)

- Literal on the left → **predicate flip**, reuse `_hl` (no `_lh`
  compares). `flipPredicate`: `slt↔sgt sle↔sge ult↔ugt ule↔uge olt↔ogt
  ole↔oge`; `eq ne oeq une` self-map.
- **Data-position gate.** Lower iff `isDataPositionCompare`. A result
  feeding `br i1`/`select i1` (even partially) is left as the original
  `i1` for Phase 4; IR stays well-typed. The flag handle never reaches a
  terminator.
- Result is always an `i32` flag handle (§1.2).

### 5.3 Driver collection & dispatch (`OpcodeLowering`)

One ordered pass (§1.4) builds `Work` (program order) + `CastW`
(captured widths, §1.3). Gated-out compares are **never enqueued** (so
never rewritten/erased). Rewrite iterates `Work`, dispatches by
`dyn_cast`, then erases all of `Work`. Each `rewriteX` performs emit +
RAUW + taint/BirthOrder bookkeeping but **does not erase** (the driver
owns erase, since `Work` *is* the set of originals).

### 5.4 Symbol/type construction (`WidthDispatch` + `TemplateName`)

`TemplateName` owns the **string**; `WidthDispatch` owns the
**`FunctionType`** and lazy `getOrInsertFunction`. The HL/LH classical
operand uses `llvmWidthType(abi)` so the IR call's argument type matches
the generated C signature (`int16_t`→`i16`, `double`→`double`). This is
the seam PRD §2.1 protects with per-symbol LIT FileCheck + link against
the generated header (no `OpcodeTables.cpp`).

## 9. Risks & mitigations

| # | Risk | Mitigation |
|---|---|---|
| R1 | **Cast width capture (§1.3).** Reading `getSrcTy()` after RAUW yields a garbage symbol. | Capture `(from,to)` at collection, before any rewrite; the WP5 zext-bridge fixture + a per-cast-pair fixture pin it. |
| R2 | **Cross-type `i1→i32` flag RAUW** would assert on an assertions-ON LLVM. | This toolchain is assertions-OFF (Phase 2 §1, confirmed); the `verify` RUN line on every compare fixture + the e2e bridge guard it. Same documented fallback as Phase 2 R5 (Value*→i32 side-map). |
| R3 | **Compare feeding both data and a branch.** | `isDataPositionCompare` leaves any branch/select-feeding compare untouched → Phase 4; the gate fixture pins "untouched + verify-clean." |
| R4 | **`-O1` reassociation surprises (PRD §2.9).** A C operator may not survive as the expected opcode. | Fixtures derived from real `-O1` output; the loud `diagnoseNoTemplate` surfaces any unhandled opcode rather than silently passing it. |
| R5 | **Driver ordering** — a consumer rewritten before its producer reads a non-handle operand. | Single program-order walk (§1.4); SSA dominance ⇒ producers precede consumers; inherited from the green Phase-2 single-loop. |
| R6 | **`_lh` surface growth vs. the Phase 8 freeze.** | Autogen-cheap; `_lh` is the faithful no-spurious-alloc representation (backend §6.2). Accepted in PRD §6. |
| R7 | **Naming drift from the yaml convention.** | Per-symbol LIT FileCheck + link against the generated header; convention frozen at Phase 10 (PRD §2.1). |
| R8 | **D1 (`OpcodeTables.cpp`) left unreconciled** → tooling implies a design the PRD retired. | WP1/WP0 aligns the yaml header + test to PRD §2.1/§5 (§11 D1). |
